# SSC — Software Supply Chain artifacts

Scan reports, SBOM diffs, and any other outputs of the `SSC/scripts/scan-all.sh`
pipeline land here. This directory is the **read-the-room** layer between
"machines produce findings" and "humans decide what to do." Reports are
committed so that:

- there is a record of what was scanned, when, and against which DB version,
- review and action notes live next to the findings rather than in a chat,
- diffing two reports across releases is one `git diff` away.

## Naming

```
SSC/reports/report<YYYYMMDD>.v<N>.md
```

- `<YYYYMMDD>` — local date the scan was run (UTC if you're in CI).
- `<N>` — 1-based counter for that day. Multiple scans per day are common
  during incident response or release-day hardening; bump the counter so
  prior reports are immutable.
- Examples: `SSC/reports/report20260506.v1.md`, `SSC/reports/report20260506.v2.md`.

`SSC/scripts/scan-all.sh` figures out the next `<N>` automatically by looking
at existing files for today and incrementing.

## Workflow (produce → assess → act)

1. **Produce.** Run `SSC/scripts/scan-all.sh` (locally or in CI). It runs the
   six scanners (Trivy, Bandit, OSV-Scanner, Hadolint, Gitleaks, Syft) over
   the current source and writes a structured markdown report into
   `SSC/reports/`. The "Assessment" and "Action" sections of that report are
   pre-stubbed but empty.

   > **This repo (TypeScript workspace):** Bandit is Python-only, so it is
   > auto-skipped when no `*.py` sources exist (recorded as `N/A` in the
   > report). Hadolint lints every `Dockerfile*` we ship (there is no single
   > root `Dockerfile`). The other four scanners run as normal.

   > **Tools missing?** `scan-all.sh` is "operate," not "install." If a
   > scanner is not on `PATH`, the script writes a `NOT INSTALLED`
   > placeholder for that tool's section and prints a banner pointing at
   > `SSC/scripts/install-sectools.sh`. Install requires explicit consent via
   > `--confirm-install-sectools` because that script downloads
   > executables from the internet — it is the ONE auditable file in this
   > repo that does so. Run `SSC/scripts/install-sectools.sh` (no flag) first
   > to read the consent banner; run with `--confirm-install-sectools` to
   > proceed. See the script header for the supply-chain posture details.
2. **Assess.** A human reads the report. For each finding: classify as
   *fix-now / fix-next-release / accept-with-rationale / false-positive*.
   Edit the **Assessment** section in the report file.
3. **Act.** When fixes land, edit the **Action** section to point at the
   commit/PR that addressed each finding. If the action is "accept,"
   capture the rationale here so a future reviewer (or auditor) doesn't
   re-litigate it.
4. **Commit.** The completed report is committed to `main`. The next scan
   produces a new report; the old one is preserved as the historical
   record.

## What's a finding's lifecycle

```
[scanner emits] → [assessor classifies] → [acted on or accepted]
        │                  │                       │
        ▼                  ▼                       ▼
   raw output         severity + decision       commit ref / waiver
```

A report is "closed" when every HIGH/CRITICAL finding has either a
commit-ref under **Action** or an explicit **Accept** rationale. Anything
else is an open ticket that should not survive a release cut.

## What this directory is NOT

- **Not the SBOM**. The SBOM lives at `sbom.cdx.json` in the repo root,
  regenerated by `SSC/scripts/generate-sbom.sh` and verified by CI.
- **Not a vuln database**. Scanner DB versions are recorded inside each
  report (`Trivy DB updatedAt`, `OSV manifest version`, etc.) so you can
  reproduce the exact run.
- **Not a substitute for review**. Static scanners catch a slice of
  problems; threat-modeling and code review catch the rest.
