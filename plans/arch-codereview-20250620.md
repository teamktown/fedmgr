## 1. OpenID Federation 1.0 Conformance Audit (draft-43)

**Findings:** The current implementation only partially meets the spec requirements for Trust Anchor, Federation (Intermediate) Entity, and Relying Party profiles. Key gaps include missing endpoints, unsigned metadata, and incomplete trust chain handling:

* **Unsigned Entity Configuration:** The trust anchor’s `.well-known/openid-federation` endpoint returns a raw JSON `entityConfig` instead of a signed JWT entity statement. According to the spec, an Entity’s configuration **must** be a signed JWT (content type `application/entity-statement+jwt`) containing its metadata. Currently, the implementation writes JSON to `entity-configuration.json` and serves it as JSON, which is not spec-compliant. This means Relying Parties and other Entities cannot verify the issuer’s signature as required.

* **No `exp` Claim or Rotation:** The entity configurations and subordinate statements lack an expiration (`exp`). For example, the trust anchor config includes `iat` but no `exp`, and subordinate configs are similarly missing expiration. The spec expects entity statements to have expiration times and defines procedures for trust anchor key rollover. The implementation should add reasonable `exp` claims (e.g. 1 day or configurable) when signing JWTs and support re-signing or key rotation for trust anchors (perhaps via a CLI command or automated process).

* **Incomplete Trust Chain Verification:** The `validateTrustChain` logic only verifies the first token in the chain with the trust anchor’s key and skips intermediate links. This will **not** detect invalid intermediate signatures or tampering beyond the first hop. The spec requires verifying each Entity Statement in the chain: each intermediate’s signature using its superior’s key, up to the trust anchor. The code should be extended to loop through `trustChain[]`, verifying `ES[i]` with the public key from `ES[i+1]` (the signer) for all links, not just the first. Any failure should invalidate the chain. Edge cases like multiple trust anchors or multiple authority hints should also be handled (e.g. choose a chain that leads to a trusted anchor).

* **Missing Federation List/Fetch Endpoints:** The implementation does not expose a `federation_list_endpoint` for trust anchors or intermediates, and repurposes the `federation_fetch_endpoint` incorrectly. In the trust anchor’s metadata, `federation_fetch_endpoint` is set to the same URL as the entity configuration (i.e. `.well-known/openid-federation`), and there is no distinct `/fetch` endpoint. The OpenID Federation spec mandates that Intermediate Entities and Trust Anchors **MUST** publish both a **fetch** endpoint and a **list** endpoint. These endpoints allow retrieval of subordinate statements and discovery of subordinates, respectively. Currently, a `/resolve` endpoint is provided (acting as a simplified resolver), but this is not a substitute for the required `fetch` and `list` endpoints:

  * **List Endpoint:** No `/federation_list` or equivalent exists. Thus, a client cannot get the list of this Entity’s immediate subordinates. Implement a `GET /federation_list` (or similar path) that returns an array of entity IDs (subordinates) for trust anchors and intermediates. This should correspond to the `federation_list_endpoint` advertised in metadata. For example, the trust anchor could list all intermediate federation entities (or leaf entities if none).
  * **Fetch Endpoint:** There is no proper `GET /federation_fetch?sub=<entityID>` endpoint returning a JWT subordinate statement. The code’s `/resolve` currently returns a dummy JSON with `trust_chain` and metadata but not the actual signed statement. We need a real fetch endpoint (e.g. `GET /fetch?sub={entityID}`) that responds with `Content-Type: application/entity-statement+jwt` and the JWT signed by this entity about the requested subordinate. This subordinate statement JWT should include claims `iss` (issuer = this entity), `sub` (subject = subordinate’s ID), metadata about the subordinate, and be signed with this entity’s private key. It corresponds to spec Section 8.1 “Fetching a Subordinate Statement”.
  * **Update Metadata:** Once implemented, update the trust anchor’s `metadata.federation_entity` to include correct URLs: e.g. `"federation_list_endpoint": "http://…/federation_list"` and `"federation_fetch_endpoint": "http://…/federation_fetch"` (and remove the incorrect reuse of `.well-known/openid-federation` for fetch). Intermediate entities should similarly advertise their own endpoints (if they run their own server).

* **Intermediate (Federation Entity) Profile not implemented:** The CLI stub for creating an “operator” (intermediate) is not implemented, and there is no code path to generate or serve intermediate entity statements. This is a major gap for the Federation Entity profile. Currently all subordinate entities are treated as RPs or OPs directly under the single trust anchor. To conform with the spec’s federation hierarchy, the system should support at least one level of intermediate federation operator:

  * Implement `fedmgr create op <name> --federation <fed>` to generate an Intermediate Entity. This would be similar to `create fed` (generating keys and an entity configuration JSON in `build/install/federations/<fed>/operators/<name>` perhaps). The new intermediate’s `authority_hints` should list its superior (the trust anchor’s entity ID). Its metadata type would be `federation_entity` (and possibly also `openid_relying_party` or OP if it plays dual roles). Initially, we can treat an intermediate as a non-active configuration that the trust anchor knows about.
  * **Issuing Subordinate Statement:** When an intermediate is created, the trust anchor must issue a JWT **subordinate statement** about it. That is, sign an entity statement where `iss` = trust anchor ID, `sub` = intermediate’s ID, containing the intermediate’s metadata (or at least its public key/JWKS and any trust marks). This JWT should be saved (e.g. in a `subordinates/` folder or in the registry) so that the trust anchor’s fetch endpoint can return it when queried for that intermediate. *Example change:* After generating the intermediate’s keys and `entity_configuration.json`, call a new function to `signJwt(intermediateConfig, anchorPrivateKey)` and save the resulting JWT to a file (e.g. `anchor-subordinate_<name>.jwt`). The trust anchor’s `/federation_fetch` can then serve this file for `?sub=<intermediateID>`.
  * **Intermediate’s Own Server (Optional):** For full compliance, an Intermediate Entity should also host its own `.well-known/openid-federation` (signed by itself) and possibly a fetch/list for its subordinates. As a first step, we might not run a separate container for intermediates, but we should be prepared to simulate that. A lighter approach is to have the trust anchor also handle serving the intermediate’s entity configuration (since it’s known and static) when requested. However, that deviates from spec, where each entity should ideally host its config at its own `sub` URL. A more correct approach is to allow starting an intermediate’s server on a new port (similar to how MCP instances are started) that will serve its `.well-known/openid-federation` and future fetch/list endpoints. This could reuse much of the federation-admin code but configured for the intermediate’s keys/metadata. **Recommendation:** Implement the creation and JWT signing first (to have the data structures in place), then plan a follow-up to allow launching an intermediate server process if needed.

* **Relying Party (Leaf) Profile coverage:** The trust anchor’s metadata currently also contains an `openid_relying_party` section, implying the federation admin might double as an RP for testing. Leaf entities (RPs or OPs) are partially handled via “MCP” instances, but improvements are needed:

However, the MCP’s metadata lacks an explicit RP or OP metadata section (it only has `federation_entity` with `trust_marks: []`). Ensure that if the system ever acts as an OP, it honors the federation registration process (which might involve resolving trust chains). This is more of a future scope, but we should keep it in mind.

* **Trust Marks:** The implementation has a placeholder for trust marks but no real issuance or validation. The trust anchor’s `/trust-mark-status` endpoint currently returns a hard-coded “active” status for any `trust_mark_id`, and `trust_marks` arrays are empty in metadata. While trust marks (optional conformance or policy badges) are not the top priority, a conformant implementation should be able to handle them. At minimum, we should:

  * Allow trust anchors (or designated Trust Mark Issuers) to issue signed trust marks (JWTs) to entities, and publish a `federation_trust_mark_endpoint` and `federation_trust_mark_status_endpoint` as per spec sections 8.4–8.6. Right now, the metadata includes `federation_trust_mark_status_endpoint` but there is no `federation_trust_mark_endpoint` or a way to obtain trust marks. We can plan a simple approach: trust anchor can issue a JWT (with type identifier and issuer) and the entity can include it in its trust\_marks list. The status endpoint can then verify and indicate if a trust mark is valid. This likely goes beyond immediate needs, but we should flag it as a gap for full spec coverage.

Similarly, implement the fetch endpoint to return signed JWT subordinate statements.

  app.get('/federation_list', (req, res) => { … })  
  app.get('/federation_fetch', (req, res) => { … })

## 3. Certificate and Key Handling Redesign

**Issue:** Currently, keypair generation for the trust anchor (and for MCP instances) occurs **inside container startup** scripts, which is problematic for repeatability and secret management. For example, `federation-admin.js` generates a new RSA key on first run if none exists, writing it to `/usr/src/app/data/keys/anchor-private.pem` inside the container. This approach makes it hard to persist keys across container restarts and to manage keys using external secret stores. It also means the container needs OpenSSL installed and runs keygen on every fresh start, which can slow startup and cause inconsistencies (different keys each time unless the volume is persisted).

**Goal:** Move certificate (key) creation **outside** the containers, using the `fedmgr` CLI or build scripts before startup. Then mount the prepared keys into the containers as read-only secrets. Additionally, design the key handling to be abstraction-friendly so that in the future we can plug in cloud secret managers (AWS Secrets Manager, HashiCorp Vault, etc.) without major changes – for now defaulting to filesystem.

**Planned Changes:**

* **Generate Keys via CLI:** Leverage `fedmgr` for key generation during the setup phase, instead of at container runtime. The CLI already does some of this: when you run `fedmgr create fed`, it executes OpenSSL to generate the private and public key files in the appropriate directory. We will rely on that behavior. Concretely, the dev workflow should be: *run `fedmgr create fed alpha` on the host -> keys and config for “alpha” trust anchor are created under `build/install/federations/alpha/keys` -> then start the Docker composition which mounts those keys.*

* **Remove In-Container Keygen:** Update the federation-admin startup code to **not** auto-generate keys if missing, or at least make it optional. Currently it does: *if no `anchor-private.pem`, generate one*. We can replace this with a check that logs an error and exits if keys are missing (so the user knows to run the CLI first). This enforces the best practice that keys are created out-of-band. In a dev environment, we could also allow an override (like an env var `FEDMGR_AUTO_KEYGEN=true` to fall back to old behavior), but by default, we want container startup to fail loudly if keys aren’t present, rather than silently create new (unknown) keys. This ensures consistency: the trust anchor’s key will remain the same across deployments unless explicitly regenerated. It’s also critical for the conformance tests, which require pre-loading the trust anchor’s JWKS – a stable key is assumed.

* **Clean Docker Mounts for Keys:** Standardize volume mounts so that the host’s `./build` directory (specifically `build/install/federations`) is mounted into the container where the app expects the keys. Based on the code, federation-admin uses `FEDMGR_FEDERATIONS_DIR` env var to determine `dataDir`. In our Docker Compose, we should set `FEDMGR_FEDERATIONS_DIR=/usr/src/app/federations` (for example) and mount `./build/install/federations` from host to `/usr/src/app/federations` in the container. That way, the container finds `anchor-private.pem` at `/usr/src/app/federations/alpha/keys/anchor-private.pem` (if we started “alpha”). This approach keeps the build artifacts (keys, configs) on the host, under version control or backup if needed, and the container sees only what it needs. We will apply similar mounts for MCP instances: e.g., mount `./build/install/mcp_instances` to `/usr/src/app/mcp_instances` so that when an MCP container starts, it finds its keys already available. Each MCP’s keys are generated by `create mcp` via CLI on host. In Docker Compose, we may run the CLI to prep multiple MCPs before bringing up containers.

* **Certificate Utility Abstraction:** Introduce a module or pattern for key handling to enable future secret store integration. For example, create a `KeyProvider` class with methods like `generateKeyPair(name)`, `getPrivateKey(name)`, `getPublicKey(name)` that by default operate on the local file system (in `build/install/federations/...`). The current code directly reads files via `fs` and spawns OpenSSL; we can wrap those in our provider. Then, if we later want to use AWS Secrets Manager, we can implement a subclass of KeyProvider that fetches the key material from AWS by name instead of reading local files. For now, we will still use file-based keys, but designing this interface decouples the storage mechanism. For example, `certificate-utils.js` could use `process.env.KEY_PROVIDER` to switch between `FileSystemKeyProvider` (default) vs others.

* **Default to On-Disk Secrets:** In the near term, our `FileSystemKeyProvider` will manage PEM files on disk (which is straightforward and aligns with how the code works today). We’ll ensure that the file paths are all under the `build/` directory. The `.env.example` can be updated to include something like `FEDMGR_FEDERATIONS_DIR=./build/install/federations` for clarity. Also, update documentation to instruct that keys will be stored on disk and should be protected (perhaps advise using file permissions or Git ignore for those). Mention that if using a cloud secret manager in future, the env configuration would differ.

* **Consistent Key and Cert Handling for MCP:** The MCP creation currently also generates keys internally using OpenSSL commands. We should apply the same refactor there. Ideally, `fedmgr create mcp` should generate the MCP keys on the host (which it does via `mcpInterface.createMcp()`), and when the MCP container (if any) starts, it just reads them. Looking at `createMcp` implementation: it writes keys to `mcp_instances/<name>/keys/` and an entity config JSON. That’s done on the host if `fedmgr` is run on host. We need to ensure the MCP docker (if we run a separate container for the MCP server) mounts the same directory. Likely, we run MCPs as child processes of federation-admin in the current design (via spawn), so they inherit access to the host file system through the volume mount. We’ll double-check that the spawned MCP processes are reading from the same `mcp_instances` folder that is persisted. (In the code, `createMcp` uses a path under `__dirname, '../../mcp_instances', name`, which in container will be inside the app directory – by mounting, we make it persistent).

* **Testing and Diff Examples:**

  * In `federation-admin.js`, remove or comment out the OpenSSL calls inside the container. For example, the block:

    ```js
    if (!fs.existsSync(privateKeyPath)) {
       console.log('🔑 Generating federation keys...');
       execSync(`openssl genrsa -out ${privateKeyPath} 2048`);
       … 
    }
    ```

    will be removed or guarded by an env flag. Instead, if `!fs.existsSync(privateKeyPath)`, we can log an error: “Keys not found – please run `fedmgr create fed` to generate keys before starting the container.” and then `process.exit(1)`. This change ensures the container won’t create unexpected keys.
  * In `docker-compose.yml`, under the federation-admin service, add a volume:

    ```yaml
    volumes:
      - ./build/install/federations:/usr/src/app/federations:ro
    ```

    and an environment variable: `FEDMGR_FEDERATIONS_DIR=/usr/src/app/federations`. Similar volumes for any other component that needs access. Marking it read-only (`:ro`) is wise for trust anchor keys, so the container can’t modify host secrets (if the app tries to rotate keys, we might deliberately mount as rw during that operation, but by default keep ro).
  * Ensure that the CLI’s output (the `build/install/federations` structure) matches what the server expects. According to the dev guide, *“build/install/federations/ – Federation configurations and keys”*, which is exactly what we’re doing. We should also verify that the registry file (fed-reg/registry.json) is stored under build (it is configured to `build/install/fed-reg/registry.json`). We will mount `build/install/fed-reg` as well if the server needs to persist the registry across restarts.

* **Secret Rotation & Multiple Environments:** Although not immediately asked, by generating keys outside and possibly storing references in .env, we open the door to support key rotation more cleanly (e.g., generate a new key, update the entity configuration with a new JWKS, etc., without container intervention). We should document how an admin could rotate keys: generate new keys with CLI (perhaps a future `fedmgr rotate fed <name>` command), update trust anchor JWKS, distribute new JWTs, etc. This planning ensures our new design doesn’t paint us into a corner.

Overall, this change will result in a cleaner separation: the **build output directory becomes the single source of truth** for all keys and configs, and containers simply read from it. This matches the intended project structure (see dev-guide notes on `build/install/federations/*/keys/*.pem` and others). By abstracting key handling, we can later inject a cloud-based secret manager by implementing the same interface, keeping our core code unchanged while boosting security for production deployments.

## 6. Admin-Level Access Enforcement (`fedmgr-admin-fed`)

**Problem:** Right now, any user who can log in via GitHub OAuth to the Federation Admin UI gets a JWT and could potentially invoke management operations. There is no concept of an “administrator” versus regular user in the system – but we need one. We want to introduce an **admin role** for the federation manager and restrict sensitive operations (like creating or deleting entities, or shutting down servers) to that role. The term “fedmgr-admin-fed” likely refers to enabling an admin mode for a given federation (perhaps the trust anchor itself acting as an admin federation). We interpret this as requiring a specific admin user identity to perform certain `fedmgr` actions, both via CLI and UI.

**Plan:** Implement a simple admin authentication check tied to a configured user in `.env`. For example, we add an environment variable in the `.env` file (and .env.example) like `FEDMGR_ADMIN_USER=<GitHubUsername>` or `<GitHubUserID>`. This will be the GitHub account allowed to administer the system. In a more complex setup, we might have a user database or multiple admins, but for now one is sufficient. Here’s how we’ll enforce admin access:

* **Marking Admin in JWT:** When a user logs in via GitHub OAuth (handled in federation-admin’s OAuth callback), we get their GitHub profile (likely includes an ID or username). In the code, after successful OAuth, we issue a JWT for the user. We can extend this JWT to include a claim indicating admin status if the user matches the configured admin. For instance, add `"admin": true` in the JWT payload for that user. Alternatively, we could include a special “trust\_mark” or a custom claim to denote roles. Since this token is only used internally, a simple boolean is fine. The token signing happens in the OAuth callback (currently using `jwt.sign` presumably with the trust anchor’s key). We will fetch `FEDMGR_ADMIN_USER` from env, and if `githubProfile.login` (username) equals that, include the claim.

* **Middleware Enforcement:** For REST API endpoints that perform admin tasks (the ones we added in section 4, like create federation, create MCP, etc.), we add an Express middleware to check `req.user` (assuming we decode JWT on requests). We might use something like `jsonwebtoken.verify` on incoming `Authorization` header to decode the JWT and attach it to `req.user`. Then the middleware simply does: `if (!req.user || req.user.admin !== true) { res.sendStatus(403) } else next()`. This ensures only the admin can hit those endpoints. We’ll apply this to routes like `/api/federations*`, `/api/mcps*`, etc. The existing UI endpoints for login or public info (/.well-known, /health) remain open as before.

* **CLI Enforcement (if needed):** The CLI is typically run by a trusted user on the host, so it may not need an internal auth check. However, if we imagine a scenario where multiple people have access to the machine or we package the CLI for others, we might want to prevent accidental misuse. One idea: require the user to provide admin credentials or have an environment variable to run certain commands. Since the CLI isn’t a long-running server, a simple approach is acceptable: e.g., for destructive commands like `delete` (if implemented) or others, prompt for confirmation or require a flag. But given our context, focusing on the web interface is the priority. The CLI can be assumed to be used by the admin directly. We won’t implement strict CLI auth, but we will clearly document that CLI commands are to be run by authorized personnel only.

* **UI Indications:** On the front-end, if a non-admin user logs in (say someone not listed as admin manages to log in if our OAuth isn’t restricted – though we could even restrict OAuth to a certain GitHub org or username), the UI should not show management options. We can check the `admin` flag in the JWT on the client side as well. If not admin, perhaps just show a message or a limited view (maybe only the fallback page with “You are logged in as user X. No admin privileges.”). This is mostly for user experience; the real gate is on the server side. But it’s good to give immediate feedback.

* **Protecting Existing Endpoints:** Consider if any current endpoints allow state changes without auth. For example, `/validate-token` is open (but it just validates a token), `/resolve` and `/trust-mark-status` are open (and should be, as part of federation API). Those are fine. The new endpoints we add are the main concern, plus perhaps things like the registry update functions. The code has a concept of “users” in the registry (currently an empty object in default), which suggests future multi-user tracking. We won’t dive into multi-user right now, but we can utilize the `users` structure to store an admin user record if needed (or just use env as single source).

* **Testing Admin Enforcement:** We will add tests to ensure that without proper credentials, management calls fail. For instance, simulate a call to `POST /api/mcps` without a token or with a non-admin token and expect HTTP 403. Also, test that with the admin token it succeeds. This gives confidence our mechanism works.

* **CLI “fedmgr-admin-fed” Meaning:** The phrasing could imply a mode where `fedmgr` itself runs with admin privileges for a given federation. It might be suggesting a separate command or flag. If needed, we could introduce a CLI command like `fedmgr admin <federation> <operation>` that internally authenticates or ensures it’s run by admin. However, since our CLI is local, we might not need that. It’s more likely the question wanted the admin concept tied to federation management. We will document that the trust anchor (federation) can have an associated admin user. Possibly, we could include in the trust anchor’s metadata a claim indicating who the admin is (not standard, but for internal use). For simplicity, we’ll not put that in public metadata; the `.env` and JWT claims suffice.

By implementing this admin gate, we significantly harden the environment. For example, if the federation admin UI were exposed, only the known admin can alter the federation; any other logged-in user could maybe view public info but not compromise trust settings. This is important even in a testbed scenario to simulate real-world access controls. We should mention in docs that `FEDMGR_ADMIN_USER` should be set to the GitHub username (or user ID) of the person who will administer the system, and that it’s recommended to keep the admin UI protected (perhaps via network controls, since OAuth alone doesn’t restrict which GitHub users can attempt login – although we could restrict by checking the username as we do).

In addition, if we ever add an “admin CLI command” (like `fedmgr grant-admin <user>`), we can tie it into this system by updating the registry’s `users` map with an admin flag. For now, one admin via env is straightforward.

**Summary:** Only the configured admin user can perform create/start/stop/delete operations on federations and entities. The system will enforce this by marking admin’s tokens and checking that on sensitive routes. This ensures separation of roles and prevents unauthorized configuration changes.

Overall, these refactors will make the codebase cleaner: smaller files focusing on one aspect (CLI parsing vs business logic vs express routes). It will be easier to navigate (one can open `create-command.js` to see all creation logic, rather than search within a huge switch). It also lays groundwork for future enhancements – e.g., adding a `delete` command becomes adding a new file rather than expanding a switch. The team should be mindful to update tests after refactoring (test specs may need to adjust import paths). Fortunately, our changes don’t alter functionality, just organization, so tests should still pass if adjusted to new module paths.

In conclusion, the code audit identifies these areas for improvement and the recommendations above provide a roadmap to implement them. Each change should be made in a focused pull request (e.g., one PR for spec compliance changes, one for test overhaul, one for key handling, etc.), including unit and integration tests to verify behavior. By addressing these points, the `@letsfederate/fedmgr` project will become more robust, maintainable, and aligned with OpenID Federation 1.0 requirements.
