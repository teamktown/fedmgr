The install assistant: three surfaces, one reframe

The goal is an assistant that helps a user install fedmgr and enable their config. Three candidate surfaces — a hosted Dify chat, the in-browser RVF-WASM widget, and a Claude skill in the code tree. They are not competitors; they answer different moments. The reframe below decides which is the primary one, then a SWOT on each, then where RVF actually earns its place.

The reframe. Install help splits into two kinds. Informational assistance answers from the docs ("what's the enroll command?"). Situated assistance reads the user's actual machine and acts ("your docker ps shows no lab; your ca/root.crt is mode 600 so Node ignored it — here's the fix"). Installs fail environmentally — a port taken, a stale build, a cert that didn't export, a daemon not running. A doc bot can only guess at those; an agent can look. So the highest-value install surface is the one that runs where the install happens — the terminal — not the one on the marketing page. That is the Claude skill. The web surfaces are the funnel that brings people to it.

Surface A — Hosted Dify RAG chat fund: top-of-funnel

Strengths

  • Zero friction — reaches evaluators who haven't cloned anything yet
  • Hosted, always-on; lives on the website next to the pitch
  • Grounded + cited (spec + docs corpus); the full build is already spec'd

Weaknesses

  • Blind to the user's machine — can't see the real error or state
  • Another service to run/pay for (compute, vector DB, reranker)
  • Separate from the terminal where the install actually happens

Opportunities

  • Captures pre-install questions → tells you what the pitch fails to explain
  • Same corpus the skill uses — build the index once, serve both
  • Natural home for the "why behind the choices" content

Threats

  • Hallucinated commands are worse than silence for a trust tool — mitigated only by strict grounding + eval
  • Corpus drift if KB isn't re-synced on merge → stale bot
  • Ops burden competes with product work

Verdict: the evaluator funnel, not the installer. Keep it, scope it to pre-clone questions, and point every "now actually install it" answer at the skill.

Surface B — In-browser RVF-WASM widget keep: zero-infra widget

Strengths

  • Already built (12 entries, 3 arcs) — sunk cost is done
  • Zero infra, zero cost, works offline; nothing to run
  • Dogfoods the project's own vector format (RVF/fedvec) on the homepage

Weaknesses

  • Q&A only — retrieves text, cannot act or reason across many docs
  • Small corpus; query-side embedding is weak until the MiniLM upgrade
  • RVF's own gotchas (cosine-on-reopen, companion .idmap.json files) make it finicky to grow

Opportunities

  • The living proof that fedvec/RVF works — a demo, not just a widget
  • Offline path for the airgapped tier (option H) — no network dependency

Threats

  • Easy to over-invest — it will never be the situated installer
  • Shipping a large RVF brain is a non-starter (500MB+); index must stay tiny

Verdict: leave it as the homepage taster and the RVF demo. Do not grow it into the install assistant — it structurally can't be one.

Surface C — Claude skill in the code tree recommended primary

Strengths

  • Situated — reads the real environment (docker state, ports, cert perms, the actual TRUST:FAIL line) and acts
  • Lives where the install happens; can drive up.sh, verify health, fix a config, re-run
  • It is what drove this whole build — proven, not hypothetical
  • Cheapest start: the fedmgr-dev skill already exists; extend it or add install-assist
  • Dogfoods the trust story — the skill/agent can itself be a trusted MCP behind waypoint

Weaknesses

  • Requires Claude Code (or an agent host) — not every user has one
  • Per-user tooling, not a hosted funnel — doesn't capture anonymous web traffic
  • Must be versioned and maintained alongside the code (a skill is a doc that rots)

Opportunities

  • Ship as a repo skill AND a published/installable one — reaches Claude Code + Agent SDK users
  • Can run the SSC scan, enroll the user's first MCP, and flip requireValidChain end-to-end — a guided first-run
  • The same guards live in gotchas.md/FAQ — the skill loads them so it never repeats a known trap

Threats

  • An agent that runs commands on a user's box needs clear guardrails (confirm destructive steps)
  • Skill/doc drift vs the code — mitigated by the structure tests that already pin the invariants
  • Ties the best experience to one vendor's agent runtime

Verdict: the primary install surface. Highest-value (situated beats informational for installs), cheapest to start (skill scaffold exists), and it dogfoods the product.

Where RVF actually earns its place — three roles, one is the sharp one

Your instinct that RVF is "assistive on the install of a user" is right, but the strongest role isn't the obvious one. RVF plays three distinct parts; rank them:

RoleWhat it meansVerdict
Retrieval index for the corpus Use RVF/fedvec as the vector store the assistant queries, instead of Dify's built-in DB or MiniLM Situational. Great for the offline/airgap tier (dogfooding + no network); oversized machinery for a 32k-word doc set otherwise. Not the default — MiniLM/Dify DB are simpler on the hosted path.
Insight-capture loop — the sharp one Embed each user's failing question / error into an RVF index; cluster it to see where installs break The strategic win. Semantic clustering of free-text failures is exactly what RVF is good at. The clusters become the next FAQ entries and docs — the assistant's failures feed the corpus that improves the assistant. Closes the loop.
Shared corpus across surfaces One RVF index both the Dify bot and the local skill consult Nice-to-have. Real, but only worth it once two surfaces are live and drifting; premature before then.

So RVF's headline role is listening, not answering: it turns the flood of install questions into a ranked map of what to document next. That is machine-assisted insight into the user's install — captured centrally, fed back as content.

Recommended strategy — portfolio, sequenced

  • 1 · Claude skill first (primary). Extend fedmgr-dev or add an install-assist skill that: detects prereqs (Node 24, docker), runs up.sh, reads real errors against the operations FAQ, enrolls the user's first MCP, and flips requireValidChain — a guided first-run with confirm-before-destructive guards. Cheapest and highest-value; the scaffold already exists.
  • 2 · Dify chat second (funnel). The hosted, cited pre-clone helper on the website; every "now install it" answer hands off to the skill. Build per docs/dify-knowledge-assistant.md.
  • 3 · RVF as the insight loop (the differentiator). Capture failing questions/errors from both surfaces into an RVF index; cluster weekly; the clusters mint new FAQ/docs. This is the part no doc bot gives you and the part that compounds.
  • 4 · RVF-WASM widget stays as the homepage taster + fedvec demo — do not grow it into the installer.

One line: the skill installs, the chat funnels, RVF listens. The web surfaces bring people to the terminal; the terminal is where situated help wins; RVF turns everyone's failures into tomorrow's docs.
