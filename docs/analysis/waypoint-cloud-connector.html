Waypoint → Claude cloud: can we, safely?

Waypoint is the trust-enforcing MCP multiplexer. The test: could a Claude cloud instance connect to our local waypoint over the internet, safely? Verdict below is from actually running it and probing every endpoint — not from reading the code.

Verdict: the transport + security are sound and fail-closed, but waypoint is not yet auto-connectable by claude.ai. It authenticates like a resource server that trusts an external IdP's tokens; a remote MCP client can't discover where to log in, because the MCP OAuth-discovery endpoints aren't served yet. Bridgeable — see the path below.

What works (verified live)

CheckResult
GET /health200 open, {"status":"ok","tools":N}
POST /mcp no token401 fail-closed, WWW-Authenticate: Bearer
POST /mcp bogus token401 (was a 500 — fixed this pass: invalid tokens now reject as InvalidTokenError)
TransportStreamable HTTP (modern MCP remote spec): POST/GET/DELETE /mcp
Bearer verificationissuer + audience + signature + exp checked against IdP JWKS; missing exp → denied
Downstream trustaccepted-anchor policy + optional cryptographic chain validation; untrusted downstreams never connect, their tools never reachable

The gaps (what a claude.ai remote connector needs)

GapStatusWhy it matters
OAuth discovery metadatamissing/.well-known/oauth-protected-resource → 404, and the 401 has no resource_metadata=… pointer. Per the MCP auth spec, that's how a client discovers the authorization server. Without it, claude.ai can't start the login flow.
Authorization server + DCRmissingWaypoint verifies tokens from an external IdP but isn't an AS and does no Dynamic Client Registration (RFC 7591). claude.ai auto-registers with the AS — it can't with an external Google/Okta IdP.
CORSnoneNo CORS headers; a browser-origin preflight would fail. Needs a proxy or explicit CORS for the browser leg.
Public HTTPS URLn/aThe VM is a private IP; Claude cloud can't reach it without a tunnel.

The safe path to actually connect it

  1. Add the MCP OAuth-discovery layer (scoped follow-up): serve /.well-known/oauth-protected-resource, add resource_metadata to the 401 WWW-Authenticate, and either become a minimal AS with DCR + PKCE or front waypoint with one claude.ai can register against. This is the real "make it a spec-compliant remote MCP server" work.
  2. Expose over HTTPS with a tunnel — e.g. a Cloudflare quick tunnel (cloudflared tunnel --url http://localhost:8077) gives an ephemeral public HTTPS URL, no inbound firewall change. Not done here — exposing the VM to the internet needs your explicit go.
  3. Add it in claude.ai → Settings → Connectors → Add custom connector → the tunnel URL. The OAuth flow gates access; waypoint's downstream trust policy gates which tools are reachable.

Safety holds throughout: /mcp is bearer-gated (fail-closed) and downstreams are trust-gated, so even an exposed waypoint won't hand an unauthenticated caller a tool — but exposure is still an outward-facing step that's yours to authorize.

What you can do today (no new code)

A non-browser MCP client with a manually-obtained bearer token from your IdP can already call the local endpoint:

WAYPOINT_CONFIG=./waypoint.json \
WAYPOINT_OIDC_ISSUER=https://accounts.google.com \
WAYPOINT_OIDC_AUDIENCE=http://localhost:8077 \
WAYPOINT_OIDC_JWKS_URI=https://www.googleapis.com/oauth2/v3/certs \
node packages/waypoint/dist/bin-http.js      # :8077
curl -s localhost:8077/health                # {"status":"ok","tools":0}
curl -s -X POST localhost:8077/mcp -H "authorization: Bearer <id-token>" ...
