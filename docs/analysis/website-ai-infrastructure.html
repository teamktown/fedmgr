letsfederate.org — AI infrastructure, compared on paper

How the advocacy site answers questions, guides assessments, captures what visitors tell us, and gets better from it — three candidate architectures scored against your actual stack (Cloudflare front, Workers, Rackspace-spot k8s, Hetzner, OpenTofu) before any infrastructure is committed. Written 2026-07-05.

0 · What the site's AI layer must actually do

  1. Answer questions consistently about OpenID Federation, MCP trust, and fedmgr — guiding visitors to key answers, not free-styling.
  2. Run guided journeys — "assess whether OIDF fits you" → the scorecard — for each audience (local dev · enterprise platform team · federation/IdP operator).
  3. Capture anonymously what visitors answered (scorecard) and asked (Q&A), so we learn whether our thesis is on the mark.
  4. Improve from that capture via a pipeline we can afford and audit — the content loop is the product's own supply-chain story applied to its website.

1 · The three candidates

grounded in rUv source

A — Static-first: RVF-WASM in the browser

@ruvector/rvf-wasm (npm v0.1.7) runs vector search entirely in the browser — "~46 KB control plane, 5.5 KB query-only microkernel, in-memory store with HNSW, no backend required" (ruvector/npm/packages/rvf-wasm/README.md). The corpus is minted in CI and shipped as a static asset; the page ingests it on load and answers queries locally.

What it is: retrieval over a curated answer corpus — semantic FAQ, not a chatbot. What it is not: generative, stateful, or self-improving. It cannot capture anything by itself (it never phones home — which is also its privacy superpower).

The honest catch — query embeddings. The corpus is embedded at build time (free, local ONNX — see §2), but the visitor's question must be embedded in the browser too. Three real options, in ascending quality/cost:

  • Hash embedder — fedvec already ships one (packages/fedvec/src/hash-embedder.ts): zero download, deterministic, works air-gapped. Crude lexical matching; fine for a FAQ where questions reuse the corpus vocabulary.
  • transformers.js MiniLM — true semantic parity with the build-time embedder (all-MiniLM-L6-v2, 384-dim), ~25 MB one-time model download, cached; still zero backend.
  • Workers AI embedding call — a 5-line Cloudflare Worker embeds the query server-side for fractions of a cent; tiny backend, but it also becomes the capture point (see C).

B — Dify + Langfuse from day one

Self-hosted Dify (RAG chat + agent flows over our corpus) with Langfuse tracing every conversation. You're proficient in both — that de-risks the ops story substantially.

  • Strengths: generative answers, multi-turn guided assessment, full conversation capture, and Langfuse's evals/datasets close the improvement loop natively — traces → annotate → datasets → prompt/content iteration. Highest capture fidelity of the three.
  • Costs: a running service (k8s on Rackspace spot or a Hetzner VM), Postgres + Redis + vector store to operate, LLM API spend per conversation, an auth/abuse story for a public endpoint, and an availability story — spot instances preempt, so the public site's core Q&A must not die when the pod does.
  • Brand risk: an advocacy site about verifiable trust that sends every visitor question to a third-party LLM needs a very clear privacy notice; it's answerable, but it's work.
recommended

C — Hybrid: static RVF tier + Dify/Langfuse guided tier, one corpus

Two tiers, one git-versioned content corpus, split by job:

  • Tier 1 — "Ask the docs" (static, free, always up): RVF-WASM retrieval on Cloudflare Pages. Instant, private, survives spot preemption, works offline — and it dogfoods the same RVF tech fedmgr uses (packages/fedvec), which is itself an advocacy point.
  • Tier 2 — "Guided assessment" (Dify, deliberate): the scorecard's conversational deep-dive and anything generative, proxied through a Cloudflare Worker to Dify on Hetzner/Rackspace, every trace landing in Langfuse. Explicitly opt-in ("this tier talks to an AI service"), which converts the privacy question into a trust demonstration.
  • The Worker is the seam: query-embedding assist for Tier 1, capture endpoint for the scorecard (anonymous aggregate → D1), and the proxy/rate-limiter for Tier 2. One small deployable, three jobs.

2 · The economical mint pipeline — your skepticism, answered head-on

The question was: "RVF doesn't sound sufficient… how can it improve based on user interaction unless we have a very economical (git pipeline?) way to mint an rvf?" Two-part answer:

2a · The mint is already economical — we built it, in this repo

packages/fedvec is the pattern: fastembed (local ONNX all-MiniLM-L6-v2, 384-dim — no API, no cost, runs in any CI runner) → @ruvector/rvf mints the single-file HNSW store, with a JSON sidecar mapping vector ids → entries. Two properties matter for CI:

  • Content-hash gated: FederationIndex.reindexIfChanged() hashes (embedder-id + documents) and no-ops when nothing changed — unchanged content costs ~0 build seconds.
  • Reopen-safe metric: vectors are L2-normalized and stored under the l2 metric (squared-L2 on unit vectors ≡ cosine), because RVF 0.2.x's cosine metric doesn't survive close/reopen — already handled in fedvec, carried into the site pipeline.
content/*.md ──┐ (git = the only source of truth) ├─ CI on merge: │ 1. chunk + front-matter → corpus.json (deterministic) │ 2. fastembed (local ONNX, $0) → vectors (content-hash gated: no-op if unchanged) │ 3. mint corpus assets for the browser (vectors + text sidecar) │ 4. syft SBOM → cosign sign → publish (the site's answers get fedmgr's own │ alongside the static deploy provenance treatment — verifiable corpus) │ 5. POST same corpus → Dify knowledge base API (Tier 2 stays in sync, same commit SHA) └─ Cloudflare Pages deploy

Cost of a full remint: MiniLM embeds a few hundred Q&A entries in seconds of CPU — it fits inside free CI minutes. There is no per-query cost afterward. And step 4 is the on-brand kicker: the answer corpus itself ships with signed provenance — "verify what the website tells you" becomes a live demo of the product thesis.

2b · How it "improves from user interaction" — an editorial loop, not online learning

Honestly: RVF never learns online, and for an advocacy site you don't want it to — an index that mutates from anonymous input is an integrity liability. The improvement loop is git-mediated:

visitors ─→ captures ────────────────┐ · scorecard answers (anon aggregate → D1) │ weekly triage: · Tier-1 queries w/ low retrieval score ("misses") ├─→ what did people ask that we answer badly? · Tier-2 Dify conversations (Langfuse traces/evals) │ where does the scorecard say we're off the mark? ▼ edit content/*.md → PR → CI remints → deploy (versioned · reviewable · provenance-signed · reversible)

Langfuse is the analytical brain of the loop (you already run it); the D1 aggregate and the Tier-1 "miss log" (queries whose best hit scored below threshold — capturable via the same Worker, still anonymous) feed the same triage. Every improvement is a commit — auditable trust, again.

6 · Recommendation & phasing

  1. Phase 1 (this session's prototype): static site + RVF-WASM "ask the docs" + client-side scorecard. Capture endpoint designed Worker-ready, stubbed locally.
  2. Phase 2: deploy the Worker (capture → D1, query-embedding assist, privacy note), wire the miss-log. Site is now learning whether we're on the mark with zero LLM spend.
  3. Phase 3: stand up Dify + Langfuse via OpenTofu on your k8s/Hetzner, connect the CI corpus-sync, launch the opt-in guided assessment tier.

Decision this defers to you: when to start Phase 3 — nothing in Phases 1–2 blocks on it, and every phase reuses the same corpus and capture schema.

7 · Honest caveats

  • rvf-wasm's store is in-memory: the page re-ingests the shipped corpus on load. At FAQ scale (10²–10³ entries × 384-dim) that's a few MB and milliseconds — fine; at 10⁵+ it isn't this architecture.
  • Hash-embedder Tier 1 is lexical, not semantic — good enough to launch, and the corpus build already uses MiniLM, so upgrading the query side (transformers.js or Worker) needs no remint.
  • Workers AI / D1 couple the capture plane to Cloudflare. Acceptable (front door is Cloudflare anyway); the content truth stays portable in git.
  • Scorecard capture is consent-noted and anonymous by design — no accounts, no emails, aggregate analysis only (your chosen posture).
