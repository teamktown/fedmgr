Interop assessment + PQC plan · 2026-08-06

go-oidfed interop & the Go stack's PQC readiness

Code-level assessment of go-oidfed/lib v0.11.1, lighthouse v0.22.1 (TA/TMI/resolver server) and offa (RP forward-auth daemon), cross-referenced against our TS wire profile — docs first, spot-checks against source and the running lab where the docs were silent. Target topology: mutual cross-anchoring (our TA + a lighthouse TA side by side, entities enrolled under both; optional third neutral root). Smoke test deliberately backlogged, not started.

Verdict: interop is very feasible — and the Go stack is ahead of us on PQC signing. The wire formats agree on every load-bearing detail (typ strings, trust_mark_type, authority_hints walk, federation_fetch?sub=, embedded jwks), and I verified live that our TA's entity configuration already advertises the endpoint metadata go-oidfed's resolver requires. The frictions are real but small and enumerated below — the top two are alg defaults (lighthouse signs ES512 by default; our verifier accepts only ES256) and trust-mark revocation (incompatible status endpoints; go-oidfed has no status client at all). On PQC: go-oidfed already ships ML-DSA-44/65/87 and hybrid composite JWS; the standards landed (RFC 9964, May 2026; Go 1.27 public crypto/mldsa, Aug 2026) — the bottleneck for a cross-stack PQC demo is now our jose v5 pin and hard-coded ES256.

Recommendation 1 — interop via mutual cross-anchoring

Run lighthouse as the second TA and cross-register through its admin API, with algs pinned to the common denominator (ES256) first. Concretely, in order:
  1. Alg alignment before anything else. Set lighthouse's signing alg to ES256 (PUT /api/v1/admin/kms/alg) or widen our verifier's allowlist to accept ES512. Do the first immediately (config-only), schedule the second anyway — a parameterized allowlist is also the PQC seam (Rec 2).
  2. Cross-register subordinates via explicit paths, not open enroll. Our entities → lighthouse via admin API (POST /api/v1/admin/subordinates with entity_id, jwks, and explicit registered_entity_types — avoids the GuessEntityTypes blindspot). Their entities → our TA via TA_SUBORDINATES/registry with fetchEndpoint. Leave lighthouse's open enroll endpoint disabled or checker-guarded (entity_id/trust_mark checker).
  3. Pin JWKS in both directions. go-oidfed silently degrades to TOFU on the TA's self-published jwks when nothing is pinned — configure jwks_file for our TA in lighthouse/offa configs, and keep our side's pinned-anchor behavior as-is.
  4. Authorize trust mark issuers on both anchors. Set TA_TRUST_MARK_ISSUERS on our TA (today it's unset ⇒ go-oidfed would accept any issuer for our mark types) and register our TMI + mark types in lighthouse's trust-mark registries so its EC publishes trust_mark_issuers covering our TMI.
  5. Verify their marks, serve them ours. Their marks verify under our verifier once alg-aligned (their claims are trust_mark_type-only — our verifier already reads that first). Our marks carry both names, so lib accepts them as-is.
  6. Third anchor (optional, later): a second lighthouse instance as neutral root, with both TAs as intermediates (lighthouse: just set authority_hints; ours: supports intermediates via fetchEndpoint entries). This makes chains cross the Go/TS boundary mid-chain — the strongest interop proof, worth doing only after the 2-TA lab is green.

Predicted friction, ranked

  1. high ES512 vs ES256: with defaults untouched, zero cross-stack verification works. Config fix on their side, one-line widening on ours. Also note: "it verifies in Go" is weak evidence — lib infers alg from key with no allowlist, so Go accepting our statements says nothing about the reverse.
  2. gap Revocation doesn't cross the boundary: go-oidfed never checks status endpoints (README: "No"), and our status endpoint isn't spec-shaped anyway. Cross-stack, a revoked mark stays valid until exp. Mitigation now: short TTLs (already our practice). Fix: implement the spec-shaped status endpoint (POST → trust-mark-status-response+jwt) alongside our legacy one — backlogged.
  3. med Enrollment strictness: lighthouse's enroll fetches and self-verifies the subject's EC with lib's exact-typ parsing; any TS-side EC quirk 400s opaquely. The admin-API path sidesteps this entirely — use it for the first pass, then test enroll as a conformance probe.
  4. med Entity-type invisibility: MCP-shaped metadata → empty GuessEntityTypes() → entity missing from list?entity_type=…. Always pass registered_entity_types/entity_type explicitly.
  5. low TOFU degradation (pin JWKS, step 3); unbounded chain depth in lib (set constraints.max_path_length on both anchors); offa's hard requirement on OP client_registration_types_supported — irrelevant until we front an actual OP, but disqualifies offa as a general-purpose probe for OP-less topologies; use it for chain/mark verification only.

Recommendation 2 — PQC readiness of the Go stack (layered)

The landscape moved under our July analysis — in our favor. Since 2026-07-05: RFC 9964 (May 2026) made ML-DSA in JOSE a published standards-track RFC (algs ML-DSA-44/65/87, new key type AKP) — PQC signing is no longer "draft/experimental"; Go 1.27 (Aug 2026) ships public crypto/mldsa + x509 support; jose npm supports ML-DSA since v6.1.0; and Node 24 on this machine already generates ML-DSA-65 keys natively (verified live, OpenSSL 3.5.7). The leader-posture line should be updated from "honest that PQC signing is draft" to "PQC signing is standardized; we ship it on a schedule."

Phase now (config + docs, no code)

  • Front lighthouse with the same PQC edge as everything else — its docs even recommend Caddy. PQC key exchange for the whole 2-TA lab from day one; zero Go changes.
  • Extend our CBOM with the Go-stack inventory when lighthouse joins the lab: ES512→ES256 (config) signature rows (quantum-vulnerable, migrate → ML-DSA, 2031), the edge-KEM row already covers transport. A CBOM that spans two implementations is a differentiator nobody else has.
  • Update the July leader-posture doc: RFC 9964 changes the "honest roadmap" message.

Phase next (our catch-up — the actual critical path)

  • jose v5 → v6 (major bump; touches all packages that pin ^5.x).
  • Parameterize the verifier's alg allowlist (oidf-verify, TMI signer) — one seam serves both interop (ES512) and PQC (ML-DSA-65, composite). This is the crypto-agility ADR the July analysis called for, now with a concrete driver.
  • Then the demo the posture deserves: a lighthouse-signed ML-DSA-65 trust mark verified by our TS verifier, and our ES256 mark verified by offa — over the ML-KEM edge. Every layer of that sentence is PQC or cross-stack. All prerequisites verified available; sequencing in backlog.
  • Composite hybrids (MLDSA65ES256) as the migration posture once draft-ietf-jose-pq-composite-sigs stabilizes — go-oidfed already implements them; treat as pre-standard.

Phase upstream (issue-ready asks for go-oidfed)

  • Verification alg allowlist: lib verifies with WithInferAlgorithmFromKey and no allowlist — accepts any alg the key implies. File as a crypto-agility/hardening issue (mirrors our own fix).
  • Trust-mark status client: the acknowledged "No" in their feature table; revocation is the one trust property that dies at the stack boundary. Offer the spec-shaped client + our endpoint as the test peer.
  • Go 1.27 crypto/mldsa migration: low-urgency dependency-reduction issue; they're on third-party ML-DSA today.
  • These are contributions to the reference OIDF ecosystem — exactly the letsfederate advocacy lane.

Backlog — explicitly not started

  • Smoke test (was Phase 3, moved here by decision): build lighthouse + offa (Go ≥1.26, GOEXPERIMENT=jsonv2, CGO for lighthouse/sqlite); run lighthouse on :7672 as second TA (fresh compose service behind Caddy); fetch both ECs and diff; cross-register via admin API per Rec 1 steps 1–4; probe with offa (pinned JWKS, required_op_trust_marks). Exit criteria: chain each way + one trust mark verified each way.

  • jose v6 upgrade + alg-allowlist parameterization (+ crypto-agility ADR).

Appendix — gotchas captured during this assessment

  • lighthouse's repo-root docker-compose.yaml is a stale unrelated example (traefik/gota) — the real deployment reference is docs/deployment/caddy.md.
  • lighthouse signs ES512 by default; nothing cross-stack works until algs are aligned (see Rec 1.1).
  • lighthouse's enroll endpoint is open to everyone unless an entity checker is configured.
  • lib's typ check is exact and case-sensitive (application/…-prefixed values rejected), and inspects only the first JWS signature.
  • lib silently falls back to TOFU on the TA's own jwks when no pinned JWKS is configured.
  • Our jose v5 pin blocks ML-DSA (needs ≥6.1.0); our verifier hard-codes algorithms:["ES256"] — promoted to docs/dev/gotchas.md.
  • Host curl (OpenSSL 3.0.13) cannot negotiate ML-KEM — PQC edge probes must use Node 24 or an OpenSSL 3.5 client (verified earlier this session; also promoted).
  • go-oidfed is pre-1.0 with real config churn (0.22 moved endpoints/trust-anchors from config file to DB) — pin lighthouse image tags in any compose work.
  • The running lab containers predate this branch (3 weeks old); live-endpoint facts above were re-verified against them and hold, but rebuild before the smoke test.
