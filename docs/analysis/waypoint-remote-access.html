Getting to waypoint from the outside — safely

How do we let Claude (or anyone we choose) reach a running waypoint without opening the barn door? This is grounded in the current MCP spec (2025-11-25) and the providers' own docs. It ends with the key questions only you can answer — those pick the path.

The one question that decides everything: where does the MCP client run?
  • Path A — on infra you control (your own cloud pod / dev box running Claude Code, or another local agent). Put both ends on a private overlay (Tailscale/WireGuard); waypoint is never public. Least attack surface, least ceremony.
  • Path B — in Anthropic's cloud (claude.ai connectors, Cowork, the API connector). The connection originates from Anthropic's cloud even for the desktop apps — a private overlay can't help. waypoint must be publicly reachable over HTTPS and gated by auth (a tunnel + OAuth). Anthropic's egress is the stable range 160.79.104.0/21.
Most real setups need both, by audience.

Transport & auth reality (what waypoint must speak)

  • Transport: Streamable HTTP (MCP 2025-11-25; the old HTTP+SSE is deprecated). One endpoint, POST/GET, optional SSE. Clients send MCP-Protocol-Version. Waypoint already does this on /mcp.
  • Auth = OAuth 2.1 + PKCE(S256), and waypoint is a resource server. Since spec 2025-06-18 the authorization server can be separate — i.e. an external IdP (Entra, Google, Okta/Auth0, Cognito). Waypoint verifies tokens; it doesn't have to be the login system.
  • The discovery handshake waypoint must implement (this is exactly what's missing today — see the connector-readiness page):
    • 401 with WWW-Authenticate: Bearer resource_metadata="https://waypoint.example/.well-known/oauth-protected-resource"
    • serve Protected Resource Metadata (RFC 9728) at that path, listing ≥1 authorization_servers
    • the client then reads the AS metadata (RFC 8414 or OIDC /.well-known/openid-configuration — both accepted in 2025-11-25, which is what makes Entra work)
    • enforce the token audience (RFC 8707 resource = waypoint's canonical URL); reject tokens minted for anything else; never forward the client's token to downstreams
  • Client registration: prefer CIMD (Client ID Metadata Documents — now the SHOULD default); DCR (RFC 7591) still works but is deprecated. Entra ID supports neither → pre-register the client (static client id/secret in the connector's advanced settings).

The trap to design around: Anthropic's backend hits your IdP's /token, /register and /.well-known/* from 160.79.104.0/21. A WAF in front of your IdP silently breaks the OAuth flow even when /mcp is reachable — allowlist that range on the IdP too.

The enterprise pattern (two CAs, one tenant, blessed MCPs)

Devs work locally; the org exposes one blessed waypoint.corp.example behind Cloudflare Access (or a self-hosted zrok/OpenZiti edge). Two trust roots compose cleanly:

  • Identity plane (who is calling): the corp's own IdP tenant — Entra / Google / AWS — federated at the edge (Access) and/or as waypoint's OAuth resource-server authorization server. This is the corp CA / corp identity leg.
  • Trust plane (which MCP is legitimate): the letsfederate CA as the federation base of trust — waypoint's downstream policy admits only MCP servers whose OpenID-Federation chain resolves to an accepted anchor and carries the required trust mark. This is the "blessed managed artifact" leg you already have (SSC gate → signed SBOM → trust mark).

Net: the edge answers "is this caller allowed in?" (corp tenant); waypoint answers "is this tool server trustworthy?" (letsfederate federation). Different questions, different roots — layered, not conflated.

When local MCPs must reach waypoint themselves

  • Same host / compose: they're on the Docker network — waypoint reaches them over stdio (spawned downstreams) or the compose service DNS. No exposure needed.
  • Dev laptop → central waypoint: Path A overlay (Tailscale) is ideal — the laptop joins the tailnet and reaches waypoint privately.
  • Across orgs / to the cloud: Path B — the same tunnel + OAuth edge, with a service-token (non-human) credential for the machine caller rather than a browser OAuth flow.

"Keep it clean and easy" — a compose tunnel sidecar

The bootstrapping burden you flagged is real. The answer is a one-service sidecar that anyone can drop next to the lab. Examples shipped under examples/tunnels/ (Cloudflare + zrok variants, with a README). Cloudflare shape:

services:
  waypoint-http:
    build: { context: ../.., dockerfile: Dockerfile.waypoint }   # :8077, OAuth-gated
    environment: [ WAYPOINT_CONFIG=..., WAYPOINT_OIDC_ISSUER=..., ... ]
  cloudflared:                        # outbound-only; no inbound ports opened
    image: cloudflare/cloudflared:latest
    command: tunnel --no-autoupdate run --token ${CF_TUNNEL_TOKEN}
    depends_on: [ waypoint-http ]     # CF dashboard maps waypoint.example -> http://waypoint-http:8077
    restart: unless-stopped

One secret (CF_TUNNEL_TOKEN), zero firewall changes. The zrok variant is fully self-hostable if you don't want a SaaS edge.

The letsfederate.com hosted option

Every path above asks the user to stand up a tunnel + an IdP relationship + discovery metadata. That's the bootstrapping tax. letsfederate.com could host the edge — a managed exposure + authorization-server + trust-anchor service — so a user runs one command and gets their-name.letsfederate.com with OAuth + federation trust already wired. It trades their setup burden for our operational responsibility (an AS and a public edge are real infra to run and secure). That's a product decision, not just an engineering one — flagged as Q7 below.

Key questions for you

  1. Client location — the fork. Are we targeting Path A (your own pods/laptops), Path B (claude.ai / API), or both? First target?
  2. Domain & DNS. Do we standardize on waypoint.<domain>? Whose domain — yours, the user's, or a hosted *.letsfederate.com?
  3. IdP for sign-in. Which authorization server do callers authenticate against — Entra, Google, AWS/Cognito, Okta/Auth0, or a letsfederate-hosted AS? (Sets the OAuth audience and whether we can use CIMD or must pre-register, e.g. Entra.)
  4. Exposure tool of record. Cloudflare Tunnel+Access (easiest production edge, SaaS) vs zrok/OpenZiti (self-hostable, org-owned) as the blessed example we ship and support?
  5. Human vs machine callers. Do we need the non-interactive path (service token / API connector authorization_token) in addition to the browser OAuth flow?
  6. Enterprise CA composition. Confirm the two-root model: corp tenant for identity + letsfederate CA for federation trust. Any org that wants its own CA to also anchor the federation?
  7. Self-host vs hosted service. Do we build only the self-host examples, or also stand up letsfederate.com as a hosted edge/AS to remove the bootstrapping burden? (Biggest scope call.)
