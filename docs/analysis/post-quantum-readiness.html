Assessment · 2026-07-05

Post-quantum readiness

Where does fedmgr's cryptography stand against a future cryptographically-relevant quantum computer (CRQC)? Grounded in the actual algorithms in the code and in the NIST PQC standards (FIPS 203 ML-KEM, FIPS 204 ML-DSA, FIPS 205 SLH-DSA).

Verdict: not quantum-resistant today — every trust-bearing signature is classical ECDSA P-256. The good news: the architecture is crypto-agile (algorithms are parameterized, the KMS is pluggable), so migration is a swap, not a rewrite. The exposure is forgeability of long-lived trust roots once a CRQC exists — not data confidentiality.
PQC readiness: 3 / 10 (agile bones, zero PQC wired)

Threat model — what a CRQC actually breaks here

  • Signature forgery, not decryption. fedmgr signs (trust chains, marks, CA, artifacts); it doesn't hold long-term encrypted secrets. So classic "harvest-now-decrypt-later" is a minor concern — the acute risk is a CRQC forging a trust mark, entity statement, or CA signature.
  • Long-lived roots are the crown jewels. The root CA and trust-anchor keys have multi-year validity. A key that must stay valid past the arrival of a CRQC is the first thing to move to PQC — the migration window is "years before CRQC," not "at CRQC."
  • Hashes are fine. SHA-256/SHA-3 lose half their bits to Grover → still ~128-bit security. The SBOM digests, checksums manifest, and digest binding don't need to change.

rUv-native option (honest)

QuDAG (qudag-crypto) is an rUv-native quantum-resistant library targeting ML-KEM-768 + ML-DSA (FIPS 203/204) + HQC + BLAKE3, built on the pqcrypto-* Rust crates — a natural fit for quantum-resistant agent-to-agent messaging.

Caveat (from QuDAG's own docs): its testing report states the ML-KEM/ML-DSA implementations are placeholder, "should be replaced with production-ready NIST-compliant implementations before deployment," and the ML-DSA command surface is labeled design-intent/proposed. So: a promising rUv-native path and a good reference, but not a production drop-in for fedmgr's trust signatures yet. For production PQC today, prefer a vetted library (liboqs / OpenSSL 3.5 provider) behind our pluggable KMS.

Recommendation

Don't rip-and-replace. Do two cheap things now: (1) capture a crypto-agility ADR so algorithm choice is explicit and swappable, and (2) run a hybrid-signature spike (ECDSA + ML-DSA composite JWS on Node 22) to de-risk the trust-mark path. Move the root CA to SLH-DSA first when we cut a real root — it's the longest-lived key and the least performance-sensitive. This keeps us shippable now and quantum-ready before it matters.
