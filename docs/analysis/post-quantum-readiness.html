Assessment + leader posture · 2026-07-05

Post-quantum: where we stand & how to lead

Grounded in the June 2026 Executive Order ("Securing the Nation Against Advanced Cryptographic Attacks") and Cloudflare's response. The headline: a credible 2026 "PQC leader" ships hybrid post-quantum key exchange at the edge + crypto-agility + a crypto bill of materials now, and is honest that PQC signing is still draft/experimental. We can hit that posture — and much of it falls out of the exposure choice we're already making.

What the EO actually requires. Binds federal agencies (and contractors via a future FAR rule, comply by Dec 31 2030). Two hard end-states: key establishment by Dec 31 2030; digital signatures by Dec 31 2031 — key exchange is prioritized a year ahead. Names only FIPS 203 (ML-KEM) explicitly; signatures handled generically (FIPS 204/205 not named). No "hybrid" or "TLS" mandate — it operates at the FIPS-standards layer. Central supply-chain move: a Cryptographic Bill of Materials (CBOM) for automated crypto-asset assessment. Frames harvest-now-decrypt-later as the reason to act on confidentiality today.

The reframe: key-exchange first, signatures second

Our earlier read was signature-centric (our signatures are all ECDSA). The EO + the ecosystem correct that: the near-term, observable win is post-quantum key exchange, because encrypted traffic can be harvested now and decrypted post-quantum. A signature only has to resist forgery live, so it has a longer runway. Cloudflare: "the transition to post-quantum encryption is well underway, while the transition to post-quantum authentication has only just begun" — and over two-thirds of browser traffic to Cloudflare is already post-quantum encrypted (June 2026) via hybrid X25519MLKEM768.

The free win — the exposure edge is our PQC key exchange. If we front waypoint with Cloudflare Tunnel (already the enterprise exposure recommendation), the client↔edge TLS is hybrid X25519MLKEM768 — post-quantum key exchange, out of the gate, with zero crypto code on our side. Reachability and PQC-key-establishment come from the same decision. That is the single highest-leverage, EO-aligned, demonstrable move we have.

CBOM — the cheap differentiator we should ship

The EO's supply-chain centerpiece is a Cryptographic Bill of Materials: an inventory of the crypto a system uses, so it can be assessed for quantum-vulnerability automatically. We're uniquely placed — we already generate a signed SBOM in init. A CBOM adds a machine-readable inventory of our own primitives:

{ "algorithms": [
    { "use": "trust-chain-jws",  "alg": "ES256", "family": "ECDSA", "curve": "P-256",
      "quantum_vulnerable": true,  "migrate_to": "ML-DSA", "deadline": "2031-12-31" },
    { "use": "edge-key-exchange", "alg": "X25519MLKEM768", "family": "hybrid-KEM",
      "quantum_vulnerable": false, "note": "PQC key establishment via edge" },
    { "use": "digest", "alg": "SHA-256", "quantum_vulnerable": false } ] }

CycloneDX 1.6 has a native cryptographic-asset component type, so this can ride the same syft/CycloneDX pipeline we already ship. Signing it with our own provenance flow makes it a verifiable CBOM — exactly the "automated crypto-asset assessment" the EO asks for.

Use OpenSSL 3.5 native (LTS to 2030) / Node 24.7+. rUv-native option (unchanged, honest)

QuDAG (qudag-crypto) targets ML-KEM-768 + ML-DSA, but its own testing report flags the implementations as placeholder / not production-ready. A reference, not a drop-in. For production PQC, prefer OpenSSL 3.5 / Node 24 native behind our pluggable KMS.

Recommendation — the shippable path

  1. Edge hybrid KEM (free, now): front waypoint with Cloudflare Tunnel → client↔edge is X25519MLKEM768. Reachability + PQC key exchange from one decision.
  2. Ship a signed CBOM (cheap, now): extend the init provenance flow to emit + sign a CycloneDX cryptographic-asset inventory. EO-aligned, differentiating, honest.
  3. Crypto-agility ADR (now): make algorithm choice explicit + swappable; document the 2030/2031 targets.
  4. ML-DSA-capable private CA (stage): add the OpenSSL 3.5 / Node 24 path as an option, ECDSA default.
  5. Signatures experimental (flagged): JOSE-PQC + cosign-PQC behind feature flags, clearly labeled, tracking the drafts.
Posture statement we can stand behind: "fedmgr does post-quantum key exchange today, is crypto-agile, publishes a verifiable Cryptographic BOM, and has an ML-DSA authentication roadmap to the 2031 federal deadline."

Roadmap note — housing artifacts

github.com/artifact-keeper is a real self-hosted universal package registry (Rust; 40+ formats). But its security is package-storage-first (GPG/RSA signing, SBOM consumption) — no in-toto/SLSA/cosign/provenance and no PQC. Fit for housing signed trust marks / attestations is weak-to-partial (dumb blob storage). It can complement as the package registry, but the trust source of truth wants a purpose-built attestation store or an OCI registry with native cosign support.
