Are we building THE trust backplane for MCP? An honest re-audit

A fresh multi-agent teardown of the codebase against its own thesis — verify (don't assume) which MCP tool servers to trust — and against its own standards (real TDD, no test lies, zero-HIGH/CRITICAL before a trustmark, minimal deps, LLM-legible logs). Dated 2026-07-05.

Method & honesty note. Seven independent agents audited one dimension each (thesis alignment · OIDF-spec conformance · security · supply-chain · DX · test honesty · code quality), each required to cite concrete file:line evidence. Findings then entered an adversarial verification pass (an independent skeptic re-opens the files and tries to refute each one). The verification and synthesis stages were cut off by a platform session limit after 61 agents / 653k tokens. So this report is scrupulous about status: four findings are marked ✓ adversarially verified (a skeptic re-checked the code and confirmed, high-confidence); the rest are marked ● found — verify interrupted (cited by the auditor, not yet independently re-confirmed this run). I have not upgraded any "found" claim to "true" — treat them as strong leads to confirm, not verdicts.

The verdict in one line: fedmgr has built a real, honest, partial trust surface — the federation documents are spec-shaped and the plumbing (KMS signing, proof-of-key enrollment, fail-closed admission) is genuine — but the trust verification layer, which is the entire thesis, has critical holes: a trust mark today is verified against a key the presenter chooses, the chain walk doesn't bind leaf keys to their issuer, and the zero-HIGH/CRITICAL SLA gates nothing in code. None of this is fatal, and — crucially — every one of these gaps, fixed, is a demonstrable letsfederate.org story. The gap between "surface" and "verification" is the site's entire narrative arc.

Dimension summaries (the honest state of each)

Thesis alignment

More than demos: the TA (SQLite subordinate registry, proof-of-key enrollment, OIDF §12 status endpoint), TMI (real ES256 signing via KMS), and waypoint (fail-closed admission wired to a live chain walk) form a genuine partial backplane, and the docs are unusually honest about scope. But the spine is TA→TMI, not TA→MCP-tool-server: no MCP server can currently be a resolvable OIDF leaf (nothing hosts entity statements for them), nothing binds the spawned downstream process to the validated identity, trustmarks aren't cryptographically checked at admission, and revocation is write-only. The single most thesis-undermining gap: a leaf-identity story for MCP servers (hosting + process/artifact binding). Without it, "verify which MCP tool servers to trust" verifies the anchor's registry, not the server you actually run.

OIDF-spec conformance

Spec-shaped at the document level (signed ES256 entity configurations at /.well-known/openid-federation with iss=sub, jwks, authority_hints, correct typ and Content-Type; fetch + list endpoints). But the verification side does not implement §10 chain-validation: the leaf configuration is never signature-verified or key-bound to the superior's subordinate statement, iss/sub/typ are unchecked, and TA keys are fetched over the network rather than pinned out-of-band — so "chain verified" reduces to "the URL served something self-consistent over TLS." Trust marks are weakest: rooted in an attacker-controllable jku header, using the renamed id claim instead of trust_mark_type, never surfaced in the trust_marks claim, and the TA never publishes trust_mark_issuers. Resolve endpoint and metadata policy are absent.

Security

Crypto plumbing mostly sound (PBES2-encrypted private JWEs, gitignored, 0600; proof-of-key enrollment with pinned ES256 allowlist + SSRF-guarded JWKS fetch; OAuth edge fails closed on missing exp). Two hard breaks reported: oci verify-trustmark hardcodes cosign identity/issuer to .+ (verifies a signature, accepts any signer), and an RSA private key is reported committed in git history. OAuth edge omits an algorithms allowlist and enforces no scopes. With the T0 public-tunnel direction, the lab's default-unauthenticated admin plane and unbounded session Map become real exposure.

Supply chain

Individual pieces are well-crafted (pure deterministic scan-gate, independent cosign cross-verification with node:crypto, honest CBOM). But SBOM→sign→push→gate→trustmark is not a chain: each stage is a side-by-side artifact with no cryptographic binding, the zero-HIGH/CRITICAL SLA is consulted by nothing, and oci verify-trustmark never verifies the embedded trustmark JWS. Cheapest high-leverage fix: one signed in-toto Statement (subject = artifact digest; predicate = SBOM digest + scan tally + gate verdict) the TMI requires before signing — plus making verify actually verify.

DX / onboarding

Two realities side by side. The new spine is genuinely good (fedmgr doctor preflight, idempotent lab bring-up with health waits, honest running.md, green 230-test suite via npm ci && npm test). But a stranger lands first on ~200 lines of dead README describing a deleted demo, three stale quickstarts contradict it, npx @letsfederate/fedmgr 404s (and couldn't publish as-is), and no doc gets a stranger from zero to an authenticated POST /mcp. The website will send strangers here — these break them.

Test honesty

Better than most (real ephemeral keys, genuine independent cross-checks for CA/SBOM/CBOM, strong negatives for OAuth-edge/selfcheck/admission). But the mandate is violated where the thesis lives: kms/src/trust-validator.ts — the 566-line production trust engine — has zero tests, and waypoint's "crypto admission" tests substitute a fakeValidator, mocking away the exact thing they claim to prove. The SLA gate is tested only as a pure function; revocation is write-only. Five most-wanted tests: (1) admission through the real validator against a forged chain, (2) issuance refused when the gate is blocked, (3) revoke-then-verify → INVALID, (4) expired statement rejected, (5) key-substitution rejected.

Code quality

Per-package runtime code is well-crafted (small files, fail-closed with invariant comments, strict TS, jose-only). But cross-cutting layers lag the project's own standards: @letsfederate/obs is imported by only 3 files while four parallel logging implementations coexist and the trust plane emits zero OTel spans; entity-statement signing is duplicated ta-server↔tmi-server; waypoint drags a 540 MB onnxruntime chain to import one 145-line policy module; and monolith-era dead scripts/env remain.

Verified findings (a skeptic re-checked these)

Critical✓ adversarially verified · high confidence

Trust-mark verification is rooted in the attacker-controlled jku header, not the federation

validateTrustmark() takes the JWKS URL straight from the JWS header (opts.jwksUrl ?? header["jku"]), fetches it (only SSRF-filtered), and returns VALID if any fetched key verifies the signature. No issuer allowlist, no requirement that jku belong to the issuer, no resolution of issuer keys via a trust chain, no trust_mark_issuers check. Anyone can self-sign a "trustmark" with their own key, host a JWKS anywhere public, and get [TRUST:VALID] — including the TMI's own startup self-gate.

packages/kms/src/trust-validator.ts:114 · confirmed: validateTrustmark and MCP verify-trustmark both use only this path; validateTrustChain is separate and never binds the mark's key.

Site demo → "A badge anyone can mint is not trust." Show a forged jku-signed trustmark being rejected because its issuer has no chain to the anchor. This is the headline bring-your-own-trust demonstration.

Critical✓ adversarially verified · high confidence

Chain validation skips §10 binding rules — leaf keys never bound, iss/sub/typ never checked, TA keys unpinned

Both chain walkers violate OIDF §10: the leaf entity configuration is only decodeJwt'd (self-signature never verified, keys never checked against the superior's subordinate statement — the core binding), subordinate-statement iss/sub are never compared to the expected entity, the typ header is never enforced, TA keys are network-fetched and self-verified (spec requires out-of-band pinning), and only authority_hints[0] is followed. Waypoint gates MCP admission on exactly this, so admission trust currently reduces to TLS + DNS of one URL.

packages/kms/src/trust-validator.ts:320 · confirmed: waypoint admission wraps validateTrustChain; a correct binding path exists in fedmgr-mcp but does not cover the walkers/waypoint.

Site centerpiece → an interactive trust-chain walkthrough where each hop shows exactly which key verified which statement, and a broken binding is visibly rejected — bring-your-own-trust made legible.

High✓ adversarially verified · high confidence

Trust-mark JWT uses the obsolete id claim, no trust-mark+jwt typ, no delegation — non-interoperable

The mark payload is {iss, sub, id, iat, exp} with header {jku} only — no typ: "trust-mark+jwt". The final spec names the claim trust_mark_type, requires the typ, and defines a delegation claim; none exist (adoption is reinvented via custom adopted_from_*). The verifier hard-wires the obsolete id too. The codebase demonstrably knows typ headers (entity statements set them), so this is a real gap, not a tooling limit.

packages/tmi-server/src/index.ts:183 · confirmed: zero code hits for trust_mark_type / trust-mark+jwt / delegation.

Site widget → "paste any SPID/CIE or OIDF trust mark and we parse it" only works once fedmgr speaks trust_mark_type — spec-exact claim names are the proof of real interop, not a lookalike.

High✓ adversarially verified · high confidence

Marks never appear in the subject's trust_marks claim; TA never publishes trust_mark_issuers

Per §3.1.2 a subject advertises marks via a top-level trust_marks array of {trust_mark_type, trust_mark}. No entity configuration emits this; fedmgr-mcp instead puts a bare string array in metadata.federation_entity.trust_marks (wrong location, wrong shape). The TA omits trust_mark_issuers, so a conformant resolver cannot discover a subject's marks or learn which issuers the federation authorizes.

packages/fedmgr-mcp/src/openid-ops.ts:59 · confirmed across TA/TMI entity-statement generation.

Site headline UX → point an AI assistant at any MCP server's entity ID and it discovers and verifies the server's supply-chain trust marks from the entity configuration alone.

Opportunities worth building (each is site material)

Opportunity

One stranger-runnable loop, run in CI

Every component exists (lab bring-up, proof-of-key enrollment, trustmark issuance, crypto admission, revocation) but nothing chains them end-to-end as a CI test — the only evidence is dated point-in-time docs. Build examples/02-trusted-mcp: enroll a real MCP server as a leaf → issue it a digest-bound trustmark → start waypoint with requireValidChain → show tools exposed → revoke at the TA → show admission flip to DENIED.

Site homepage demo → "deploy OIDF for MCP in five minutes" — and running it in CI keeps the site's claims perpetually true.

Opportunity

A public /resolve endpoint

Missing today. The Resolve endpoint returns a subject's chain-verified, policy-resolved metadata and validated trust marks in one signed response — the one call an AI client actually wants (and mandated on TAs by Italy's SPID/CIE profile).

Live API → paste an MCP server's entity ID, get back its verified metadata and trust marks — OIDF-with-AI in a single HTTP call.

Opportunity

A closing "here is your trust ecosystem" inventory from init

init ends with only a log line; the minted artifacts (root CA, signed SBOM, cosign keypair, TA/TMI URLs, gate verdict) are visible only as scrollback. Add a final summary block (+ --json) and/or a fedmgr status that re-derives it idempotently (doubling as a drift detector).

Money screenshot → the moment bring-your-own-trust becomes tangible.

What this means for the build order

  1. Close the verification gap before anything else — one shared §10 verifier that pins the TA key out-of-band, binds leaf keys to subordinate statements, checks iss/sub/typ/exp, and verifies trust marks via the chain + trust_mark_issuers (kills both criticals). This is the product.
  2. Bind the supply chain — one signed in-toto Statement tying artifact digest + SBOM digest + scan verdict, required by the TMI before it signs, and make oci verify-trustmark actually verify signer + JWS + digest.
  3. Test where the thesis lives — the five missing tests on the real validator; delete the fakeValidator substitution.
  4. Make revocation mean something — a verifier that consults trust-mark status.
  5. Fix the front door — one true quickstart, kill the dead README, publishable package — because letsfederate.org sends strangers straight here.

The through-line: fedmgr's honesty is its asset. The docs already admit most of this; the audit just made the list concrete and ranked. Fixing items 1–2 turns "spec-shaped surface" into "verifiable trust" — and each fix ships as a letsfederate.org demonstration, so the roadmap and the advocacy site are the same backlog.
