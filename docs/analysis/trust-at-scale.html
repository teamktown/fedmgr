Deep design · 2026-07-05

Trust at scale

Three questions that sit underneath "how do we connect waypoint": (1) once I'm signed into Claude and reach waypoint, do I authenticate again downstream — and where does a federation-minted token fit? (2) how do we find trustworthy MCPs at scale without one vendor becoming the gatekeeper — the trustmarket? (3) how does an enterprise make waypoint the governed MCP without taking away dev freedom?

1 · The token flow: two different kinds of "trust"

You sign in once. The rest is waypoint marshalling — because "who is calling" and "which server is trustworthy" are different questions answered by different credentials.
Identity plane OAuth / OIDCTrust plane OpenID Federation / CA
AnswersWho is calling? (the human/agent)Which server is a legitimate, blessed MCP?
ArtifactAccess token (JWT), audience-bound (RFC 8707), short-lived, from your IdPEntity statement + trust mark, signed up to a trust anchor / the letsfederate CA
Who mints itEntra / Google / Okta …Trust Anchor + Trustmark Issuer (the CA-rooted chain)
Where it's checkedwaypoint's OAuth edge, on every /mcp callwaypoint's downstream policy, at admission (accepted-anchor + chain + mark)

So: do you auth again downstream? No.

  • Leg 1 — client → waypoint (identity): Claude runs OAuth 2.1 + PKCE once; the token's aud is waypoint's canonical URL. waypoint verifies it. This is the only sign-in the human does.
  • Leg 2 — waypoint → downstream (trust, not identity):
    • Local/spawned MCPs (stdio): waypoint already admitted them by federation policy; it just marshals. No re-auth.
    • Remote MCPs (HTTP): waypoint is the client to them and presents its own credential — a machine/service token, or its federation identity. Not your user token.
    • If a downstream needs to act as you (delegation): waypoint does token exchange (RFC 8693) — swap your inbound token for a downstream-scoped one (aud=that MCP), preserving your identity in the act claim. Still no second prompt.

Where "the JWT with the CA" and a "federation-minted token" fit

The CA-signed chain is a trust artifact ("this server is a blessed federation member"), not a user-identity token. They're complementary axes. The clean composition:

Claude ──(1) user access token, aud=waypoint──▶ waypoint  [verifies identity]
                                                  │
                        (2) admission: is downstream federation-trusted?
                             chain → accepted anchor + required trust mark   [verifies TRUST]
                                                  │
   ┌──────────────────────────────────────────────┼───────────────────────────────┐
   ▼ stdio: marshal (no auth)     ▼ remote: waypoint's service/federation cred      ▼ delegated: token-exchange
                                                                                     (aud=downstream, act=user)

Yes, a federation-minted token is usable — as the credential waypoint presents downstream to prove entitlement (trust axis), and/or as the target of a token-exchange that binds your identity to a federation-scoped audience. The mistake to avoid is conflating it with the user identity token; keeping the two axes separate is what lets governance and delegation compose.

2 · The trustmarket — discovery without a gatekeeper

OpenID Federation is deliberately multi-anchor: a verifier chooses which trust anchors it accepts. That is the structural answer to "what if Anthropic becomes the root" — there is no single root unless we build one.

The capture risk, defused

If Anthropic adopted OIDF and became "federation implementation #1," the fear is they'd gatekeep which Trustmark Issuers are approved — a stranglehold. But federation doesn't have a root; it has anchors you choose. letsfederate is one anchor among many; Anthropic could be another; an enterprise's corp anchor another. A relying party sets its own acceptedAnchors. The defense against capture is architectural: don't accept a single root.

"Ingest theirs, remint?" — yes, trust-mark composition

You don't need to be the root to add value. letsfederate can ingest another issuer's mark as evidence and issue its own augmented mark ("letsfederate certifies X — based on Anthropic's mark plus our SBOM + zero-HIGH-CVE gate"). The mark carries the evidence / adopted_from lineage. An enterprise ingests both and remints their corporate mark. Multi-issuer, layered, no single choke — federation working as designed.

What the trustmarket is

Federation gives verifiability (is this chain valid? does it carry mark X?). At scale you also need discoverability and reputation. The trustmarket (letsfederate.org/trustmarket) is the layer on top:

  • An index of MCP entities across multiple anchors — with their trust marks, provenance (SBOM + signature), and reputation signals.
  • Queryable by trust, semantically — this is exactly what fedvec (our local semantic search over federation entities) is for: "find a trustworthy calendar MCP, anchored to an anchor I accept, carrying a valid trust mark and a clean SBOM."
  • A market, not a registry-of-one: multiple issuers/anchors "certify," verifiers "shop" with their own acceptance policy. Trust marks are the listings; anchors are the certifying bodies.

Embracing trust indicators at scale (the stumbling block)

ProblemScalable answer
Resolving full chains at call time is expensivePrecompute a cached trust receipt / witness (a signed, dated statement of "chain valid + marks present"), refreshed periodically; verifiers check the cheap receipt and spot-check.

3 · Enterprise tabletop — waypoint as the governed MCP

"Let devs use Claude locally, but make fedmgr waypoint THE MCP they connect to — so we marshal, govern, and get telemetry corporately." Here's how that plays out for Acme Corp.

The setup

  • Corporate trustmarket registry — Acme security curates: accepted anchors (letsfederate + Acme's own corp anchor), the blessed MCP catalog, and the remint policy (e.g. "only MCPs with a clean SBOM + an Acme mark"). This is their slice of the trustmarket.
  • One endpoint — waypoint.acme.example (Cloudflare Tunnel + Access → Acme's Entra tenant). Every dev's Claude adds this as its MCP connector. waypoint admits only Acme-blessed downstreams.
  • Governance overlay — because everything funnels through waypoint: telemetry (every tool call, who/what/when — the OTel spans we built), policy (trust gate + zero-HIGH-CVE gate + data-egress controls), central revocation, and signed audit of what the corporate AI could touch.

Dev freedom, preserved

Devs still pick from the blessed catalog and still run their own local MCPs for their personal dev loop. What's governed is the corporate AI plane — what the company's assistant can invoke — and that's waypoint-mediated. "Do your thing; the AI/MCP governance plane is overlaid, not in your way."

Walkthrough

  1. Security curates the corporate trustmarket: accept anchors, bless MCPs, set the gates.
  2. Platform deploys waypoint.acme.example (tunnel + Access → Entra SSO).
  3. A dev adds the one connector in Claude; Entra SSO signs them in (one auth).
  4. Dev: "use the Jira MCP" → waypoint checks it's Acme-blessed → admits → marshals → logs the call.
  5. A new CVE hits an MCP → the SSC gate flips → waypoint blocks it corp-wide; telemetry shows the blast radius instantly.
  6. Audit: security queries the trustmarket + waypoint telemetry — "what MCPs did engineering's AI touch last quarter, and were any ever un-blessed?"

Net: one sign-in, governed fan-out, full telemetry — the "overlay AI and MCP governance without blocking devs" outcome. waypoint is the chokepoint by design, which is exactly what makes it the control + observability plane.

4 · Impact of the MCP 2026-07-28 release candidate

The RC goes stateless — and that direction is good for a governed trust chokepoint like waypoint. It's breaking but not yet final (locked May 21 2026, publishes 2026-07-28); 2025-11-25 stays valid, so we version-negotiate rather than scramble.

What the RC changes

  • Stateless transport: removes Mcp-Session-Id, the initialize/initialized handshake, the standalone GET SSE stream, and SSE resumability. Per-request _meta carries protocol version + client identity + capabilities; a new server/discover RPC (MUST) advertises the server; cross-call state becomes explicit server-minted handles passed as ordinary tool arguments. Still one POST endpoint; SSE is now optional and per-request. New routing headers Mcp-Method / Mcp-Name.
  • Auth tightens (resource-server model unchanged): CIMD formally replaces deprecated DCR; RFC 9207 iss validation; application_type at registration; credentials keyed to (and non-reusable across) issuers.
  • Extensions become first-class (reverse-DNS ids; MCP Apps + Tasks ship as extensions); OpenTelemetry trace-context (traceparent) is documented in _meta.

Score against our approach — mostly tailwind

RC changeEffect on fedmgr / waypoint
Stateless + Mcp-Method routingWin. waypoint can run behind a plain round-robin load balancer — the enterprise "one governed endpoint at scale" story gets easier, no sticky sessions / shared session store.
Server-minted handles as tool argsWin, and on-theme. A federation trust receipt / capability is naturally a server-minted handle the model passes back — trust state as an explicit, composable argument instead of hidden transport metadata.
OTel trace-context in _metaWin. Our @letsfederate/obs spans propagate natively across the MCP boundary — corporate telemetry/governance becomes end-to-end without bolt-ons.
CIMD over DCR + iss validation + credential bindingReinforces the plan. The OAuth discovery layer we already said to build is exactly right — just target CIMD first and add iss checks.
Extensions mechanismOpportunity. A reverse-DNS org.letsfederate/trust extension could advertise federation trust metadata (anchors, marks) as a first-class capability.
Per-session transport Map (waypoint today)Debt. Valid for 2025-11-25, dead-end for the RC. Don't deepen it; add a stateless path selected by MCP-Protocol-Version.

Our stance

Build the OAuth discovery layer now against 2025-11-25 (it works with claude.ai today and every auth piece is RC-forward), and make waypoint's HTTP handler stateless-ready — read identity from _meta, add server/discover, keep the per-session path only as a negotiated fallback. Treat trust as a server-minted handle, which the RC now blesses as the idiomatic pattern. Net: the RC doesn't invalidate our direction — it validates it and makes the enterprise-scale + telemetry story cleaner. Watch the 2026-07-28 finalization and the Tier-1 SDK betas before committing RC-only code.
