# Operations FAQ — symptoms, causes, prevention

Every entry here is something that actually happened. Format: the symptom you
see, the real cause, and what now prevents it (a test, a script, or a rule).
The terse rule-book version lives in [`dev/gotchas.md`](dev/gotchas.md); this is
the Q&A superset for operators and for the assistant knowledge base.

## Lab & compose

**Q: The lab "forgot" my enrollments after a restart.**
Cause (historical): the TA's SQLite db lived on `/tmp` inside the container and
`down.sh` ran `docker compose down -v`.
Now: state lives on the `ta-data` named volume (`/data/ta.db`) and `down.sh` is
non-destructive by default — `--wipe` is the explicit reset. Guarded by a
repo-structure test and provable any time with `./deploy/lab/verify-durability.sh`.

**Q: After a lab restart, `https://localhost:9443` connection-resets even though every container says "Up".**
Cause: Caddy and entity-host share ta-server's network namespace
(`network_mode: service:ta-server`). Restarting the *owner* creates a fresh
namespace; the followers' listeners are stranded in the dead one. `docker
compose up -d` won't fix it — compose sees them as unchanged-and-running.
Now: `up.sh` restarts the followers *after* the owner. Rule: **netns followers
restart after their owner, always.**

**Q: TLS fetches fail with `UNABLE_TO_GET_ISSUER_CERT_LOCALLY` only *inside* a container (curl from the host works).**
Cause: Node loads `NODE_EXTRA_CA_CERTS` **once at process start**, and if the
file is missing or unreadable it prints one warning and continues with default
CAs — it does not fail, it does not retry. A root exported after boot, or one
readable only by another uid, is silently ignored.
Now: `up.sh` exports the root with `chmod 644` (it's a *public* cert), compares
**content** (not existence — a `--wipe` regenerates the CA), and restarts the TA
pod when it changes. Rule: after any root change, restart every Node process
that must trust it.

**Q: Bare `docker compose up` fails but `./deploy/lab/up.sh` works.**
Cause: keys are generated by `up.sh` (step-cli) before compose starts, and the
TLS root export/restart dance also lives there. `up.sh` *is* the lab's entry
point; the compose file alone is not the whole contract (assessment R2 tracks
closing this gap).

## TLS, identities & the URL guards

**Q: `[TRUST:FAIL] … uses http: which requires an explicit FEDMGR_ALLOW_ORIGINS exception` — what do I do?**
That's option G working. Add the *exact origin* (scheme://host:port) to
`FEDMGR_ALLOW_ORIGINS` for that process — per-origin, comma-separated, empty by
default. Do **not** reach for `NODE_ENV=development`: it is process-global,
also changes unrelated Express/library behavior, and is deprecated here.
Residual risk of an excepted origin is staleness/availability, never
authenticity — the OIDF chain is signature-rooted against pinned anchors.

**Q: Why did switching the lab to https force re-minting and re-enrolling everything?**
The scheme is part of the origin, and the origin *is* the entity identity that
gets baked into signed statements. `http://x` and `https://x` are different
entities. This is why laptop-lab identities are treated as **disposable**
(re-minting is `up.sh`-cheap) and only *shared* identities (org anchors,
published MCPs) must be minted once, in production form, and never churn.

**Q: Enrollment rejects my `jwks_url` with `origin_mismatch`.**
The TA requires `jwks_url` to share the entity_id's origin — proof you control
the identity's origin, preventing "enroll victim's id with attacker's keys."
Serve the JWKS from the same origin as the entity id (the lab's entity-host +
Caddy give every leaf `https://localhost:9445/mcp/<name>/…` for both).

**Q: Enrollment rejects a perfectly reachable IP URL with an SSRF error, even in dev.**
Private-range IP *literals* are blocked unconditionally unless that exact
origin is allowlisted. Hostnames are not resolved before checking (a known,
documented gap — resolve-time checking is a roadmap item), so use a name or an
explicit `FEDMGR_ALLOW_ORIGINS` entry, and treat the allowlist as the honest
mechanism for private targets.

## Enrollment & trust chains

**Q: `verifyTrustChain` returns INVALID with "no subordinate statement" right after I enrolled.**
Check the three-legged identity agreement: the leaf's *hosted* entity
configuration (its `iss`/`sub`), the id you enrolled with, and the id the
verifier resolves must be byte-identical URLs. A stale statement file from an
earlier origin (http vs https, old port) is the usual culprit — re-mint with
`fedmgr entity config` and re-enroll.

**Q: Waypoint denies my downstream with `requireValidChain` even though `check_trust_chain` says VALID.**
Waypoint validates with *its own* process env: it needs the anchor pinned
(`WAYPOINT_ANCHOR_JWKS`), the TLS root (`NODE_EXTRA_CA_CERTS`), and — if any
identity is an excepted origin — the same `FEDMGR_ALLOW_ORIGINS`. The MCP tool
you compared against ran with *different* env. Compare envs first.

**Q: My downstream MCP server can't see an env var I exported before starting Claude Code.**
The MCP SDK's stdio transport strips the parent environment to a safe default
set (HOME, PATH, …). Anything a downstream needs must be declared in
`waypoint.json` under that downstream's `env` — explicit beats inherited for a
policy-enforcement point. (This was waypoint's first dogfood fix.)

**Q: I changed `waypoint.json` and nothing happened.**
Waypoint reads its config once at spawn, and Claude Code keeps the stdio server
alive for the session. `/mcp` → waypoint → reconnect (or restart the session).

## Node, npm & dependencies

**Q: `npm install` succeeded but my `overrides` didn't change anything.**
npm does not re-resolve overrides added to an *existing* lockfile — stale
resolutions stay. Regenerate (`rm -rf node_modules package-lock.json && npm
install`) and verify with `npm ls <pkg>`.

**Q: A dependency major-bump passed the whole test suite, then broke in production-like use.**
The tar 6→7 lesson: fastembed's tar usage only executes at model-download time
— no test exercised it. Rule: **test suite ≠ risk path.** Identify the actual
runtime path the change affects and run it for real (we downloaded the model
and embedded). See also `scripts/patch-fastembed.cjs` for the surviving shim.

**Q: Random `SyntaxError: Invalid or unexpected token` deep inside node_modules.**
Disk-full (ENOSPC) NUL-corrupts files; `npm install` won't refetch (versions
match). Detect: `grep -rlI $'\x00' node_modules --include=*.js`. Fix: clean
reinstall. And native addons: npm 11 skips install scripts — rebuild
`better-sqlite3` (and friends) explicitly.

**Q: `node --test test/` reports one failing test called "test".**
Node 24's bare-directory form misbehaves; use a glob (`node --test
test/*.test.mjs`). Also: the default reporter is `spec`, so count with
`ℹ tests|pass|fail`, not TAP markers.

## Testing & verification discipline

**Q: The suite "passed" but something was clearly broken.**
Check how the exit code was read. `npm test | tail` reports **tail's** exit
code — the session's own near-miss. Capture `EXIT=$?` from the command itself.
Related: green output ≠ ran-at-all — our test scripts echo explicit exit
markers for this reason.

**Q: Tests touching the TA store all fail with 500s.**
`SqliteFederationStore` requires an explicit `migrate()` after construction —
the constructor only opens the db. Match the server boot path in tests.

**Q: A directory move leaked files that were supposed to be gitignored.**
`.gitignore` rules are path-anchored: moving `packages/*/keys` to
`services/*/keys` silently un-ignored key material (caught before push, once).
Rule: after any move, `git check-ignore` the sensitive paths. Guarded now by
the no-tracked-key-material structure test.

**Q: Docker image builds broke after adding a package import, but host builds pass.**
Host `tsc -b` sees the whole workspace; the Dockerfile only COPYs what it's
told. When service A gains a dependency on package B, the Dockerfile needs B in
both stages. Rule: **verify by running the lab and hitting a live endpoint**,
never by host build alone.

**Q: How do I prove the lab's durability/TLS contract quickly?**
`./deploy/lab/verify-durability.sh` (state survives a full down/up) and
`npm run test:structure` (compose invariants: named volume, no /tmp db,
non-destructive down, Caddy/netns/ports, no NODE_ENV on the TA). Both are
cheap; run them after touching anything under `deploy/lab/`.
